Далее идем СХЕМА, с строгими ПРАВИЛАМИ, создания СПЕЦИФИКАЦИИ функции obsidian (серверная часть)

```
Идентификатор - <string>
  Правила:
    - одна строка
    - уникален в пределах проекта
    - не содержит пояснений в скобках
    - не меняется при правках логики (если функция та же)

Описание - <string>
  Правила:
    - одна строка
    - начинается с глагола/действия (что делает)
    - без деталей реализации
    - без перечислений таблиц/статусов

Точка входа - <string>
  Правила:
    - одно значение, точное имя entrypoint (как в коде/деплое)
    - без альтернатив

Таймаут - <number> сек
  Правила:
    - число + "сек"
    - без диапазонов и "по умолчанию"

<пустая строка>

---

<пустая строка>

На входе:
  Правила:
    - раздел описывает только то, что приходит извне (headers/body/query/path)
    - не описывает проверки, валидацию, ошибки, преобразования
    - формат строго "->" + описание

    Структура:
      -> `Header-Name: <format>`: <назначение>
      -> `field_name`: <описание> (указать где: в теле запроса / query / path, если не очевидно)

    Обязательность:
      - если обязательное: указать словами прямо в этой строке ("обязателен/обязательно")
      - если опциональное: указать ("опционально")
      - не использовать двусмысленности ("желательно", "обычно")

Внутренняя работа:
  Правила:
    - раздел описывает только фактическую последовательность действий
    - порядок строк = порядок выполнения
    - формат строго "->" и вложенность через табы/отступы
    - каждое условие оформляется отдельным подпунктом внутри конкретного шага
    - без объяснений "почему", без архитектурных рассуждений

    Допустимые типы шагов (как в исходнике):
      -> Логирование: <что выставляется/что логируется>
      -> Авторизация:
        -> <проверка 1>
        -> <проверка 2>
        -> <результат проверки/извлекаемые поля>
      -> Парсинг запроса:
        -> <что извлекается> с помощью <конкретная утилита/модуль>
      -> Генерация ID: <чем генерируется> (UUID и т.п.)
      -> Получение <данных>:
        -> Подключение к <конкретная БД> для <конкретный запрос/цель>
        -> Если не удалось получить, установка значения по умолчанию "<значение>"
      -> Транзакция в <конкретная БД>:
        -> <проверка/селект, зачем>
        -> <вставка/обновление 1: таблица + ключевые поля>
        -> <вставка/обновление 2: таблица + ключевые поля>
      -> Завершение: <что логируется/что важно отметить>
      -> Обработка исключений: <что логируется> и <какие статусы возвращаются в общем виде>

    Правила формулировок:
      - каждый подпункт должен быть проверяемым (можно подтвердить по коду/логам/БД)
      - не использовать "и т.д.", "прочее", "дополнительно", "в том числе" без перечисления
      - если пишешь "не создаются" / "не выполняется" — только если это важно для текущей версии

На выходе:
  Правила:
    - перечисляются ВСЕ конечные варианты ответа
    - формат строго:
      -> `<HTTP_STATUS Name>`: <тело ответа или описание, когда без тела>
    - для каждого статуса обязательно указать условие ("Если ...")
    - тело ответа пишется точно (ключи, строки, формат)
    - никаких "может вернуть" — только "возвращает"

  Минимальный набор (если применимо к функции):
    -> `2xx ...`: успешный ответ + точное тело
    -> `400 ...`: ошибка входных данных/парсинга + условие
    -> `401 ...`: авторизация + условие
    -> `409 ...`: конфликт (если есть бизнес-ограничение) + условие
    -> `500 ...`: неожиданные/инфраструктурные ошибки + условие

<пустая строка>

---

Зависимости и окружение
  Правила:
    - только конкретные зависимости и переменные окружения
    - никаких объяснений реализации зависимостей
    - формат списков как в исходнике (дефисы)

- Необходимые утилиты: `<path>` (<что делает в 2-4 слова>)
  Правила:
    - перечислять только реально используемые утилиты
    - путь указывать точный (как в репозитории)
    - описание в скобках короткое, без деталей

- Переменные окружения:
  - `<ENV_NAME>` (<к чему относится в 2-6 слов>)
  Правила:
    - только те, которые реально читаются в рантайме
    - без значений и без инструкций "как настроить"
    - если переменные относятся к разным БД/сервисам — группировать как в исходнике отдельными строками

ОБЩИЕ ОГРАНИЧЕНИЯ ФОРМАТА (ЧТОБЫ НЕ БЫЛО ЛИШНЕГО)
- Никаких разделов сверх указанных: только (шапка) + На входе + Внутренняя работа + На выходе + --- + Зависимости и окружение
- Никаких примеров "например", если пример не является частью контракта
- Никаких ссылок, мотивации, обсуждений архитектуры
- Никаких альтернативных реализаций или "в будущем"
- Одна строка = один факт
- Вся логика — только в "Внутренняя работа", а все данные — только в "На входе" / "На выходе"
```
